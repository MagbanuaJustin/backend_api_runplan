## 1. What this project is (my inference)

A **headless REST API for a running-training planner**. A runner registers, saves a
profile (goal, experience, race date, available days), the API *generates* a periodised
plan (base → build → taper) as dated sessions, the runner approves it, logs activities,
and the plan can be **rebuilt from what they actually ran**, keeping completed sessions.

**Open question:** is there a frontend already built against this, and is its expected JSON
shape fixed? If yes, response shapes are a contract and I will not change them without asking.

## 5. Data-layer state (correcting my own earlier worry)

All **42** `->raw()` calls use `?` placeholders — **no SQL injection**. The actual problems:

1. **Controllers hit the DB directly.** `Auth.php` uses `$this->db->table('users')`; `Plans::rebuild`
   embeds the 21-day `MAX(distance_km)` query. There is **no `UserModel`** and no session model.
2. **Models extend `Model` but ignore the ORM** — no `$table`, `$fillable`, `$timestamps`, or
   `query()`. LavaLust's builder (`find_by`, `update_where`, `paginate`, `transaction`, relations) is unused.
3. `plan_revisions` unique key is `(plan_id, version)` and `approve()` inserts a revision **without**
   bumping `version` — currently unreachable, but fragile.

## 6. Known bugs to fix

- **[live] `PlanModel::build()` guard mismatch** — `weeks < MIN_WEEKS[$goal]` returns the
  *"more than 30 weeks away"* message (wrong advice), and the `weeks > MAX_WEEKS` upper bound was
  **deleted**, so a race 52 weeks out produces a ~1-year plan unchecked. `MAX_WEEKS` is now
  referenced only inside a string.
- **[minor] `Sessions::update`** — sending both `scheduled_date` and `status` silently ignores `status`.
- **[housekeeping] 8 junk files still tracked** (`$r`, `$t`, `'Race`, `curl.exe`, `findstr`, `php`,
